## 3. 建议的正式目标

以下是建议值，需客户确认后作为验收指标：

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 数据库 RPO | <= 1 分钟 | 独立节点复制或托管 MongoDB PITR；不是每分钟跑一次全量 dump |
| 附件 RPO | <= 1 分钟 | 独立对象存储/第二台主机，上传完成后校验并确认复制状态 |
| RTO | <= 30 分钟 | 备用运行时可启动、域名/隧道可切换、恢复抽查通过 |
| 全量恢复点 | 每日 1 次，保留 7 个日点、4 个周点 | 用于误删、勒索和长时间回溯 |
| 恢复演练 | 每周自动校验、每月人工抽查 | 必须验证数据库记录和附件字节/哈希 |

“实时”需要区分两种模式：

1. **近实时（推荐先做）**：复制延迟通常小于 1 分钟，但网络中断时会产生明确的待同步队列。
2. **同步写入**：关键数据库写入必须得到独立节点确认，数据库可以接近零数据丢失；附件仍需独立存储确认，网络延迟和可用性成本更高。

## 4. 实施架构

### 4.1 MongoDB

- 在独立物理主机、独立云主机或托管 MongoDB 上建立副本/PITR 目标，不能与应用和 C 盘共用同一故障域。
- 先从当前已验证快照做初始同步，再启动 oplog/连续日志复制。
- 对关键写入使用持久化写关注配置；切换前验证副本延迟、重启恢复和读写权限。
- 不把单库 `mongodump` 每分钟执行当作实时方案；它会产生高 I/O，且不能覆盖两次 dump 之间的故障窗口。

### 4.2 上传附件

- 将 `UPLOAD_PATH` 迁移到支持版本控制/保留策略的独立对象存储（S3 兼容、OSS、COS 或独立 MinIO），或第二台主机的专用存储卷。
- 文件先写入临时对象，完成大小和 SHA-256 校验后再标记为可用；数据库 `FileAsset` 记录复制状态和最后成功时间。
- 过渡期可以用每分钟增量同步和校验，但同步目标必须位于另一台主机/另一云区域，不能是 C 盘或同一物理机的普通目录。

### 4.3 监控与告警

- 每分钟写入复制心跳，记录数据库复制延迟、附件队列长度、最后成功时间和目标可达性。
- 连续两次失败或延迟超过 2 分钟即标记 `DEGRADED`，通过已验收的外部 webhook/短信/企业微信告警；Windows Event Log 只能作为本机辅助证据。
- 发布门禁检查“最近成功复制时间”和“恢复点可读性”，不满足就禁止宣称已完成或删除旧恢复点。

### 4.4 长期恢复点

- 保留现有每日全量备份、manifest、逐文件 SHA-256 和隔离恢复演练。
- 每个恢复点至少保留一份独立副本；副本复制完成后再出具 receipt，不能只复制 `manifest.json`。
- 每月在全新数据库和附件目录做一次完整恢复，保留报告和签字。

## 5. 上线门禁

1. 客户提供独立灾备目标（第二台主机、NAS 或对象存储）及批准的访问方式。
2. 以当前恢复快照完成初始同步，核对 34 个集合、8,736 条文档和 426 个附件。
3. 连续运行至少 24 小时，记录复制延迟、断网重连、重复文件和校验失败。
4. 做一次“主机断电/应用切换”演练，确认 RTO、域名切换、登录、运输提报和附件读取。
5. 客户签字后才启用正式写关注/对象存储切换；在此之前保持现有恢复实例和旧恢复点可回滚。
